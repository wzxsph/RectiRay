# Reproduce RectiRay

[English](reproducibility.md) · [简体中文](../i18n/docs/reproducibility.zh-CN.md)

RectiRay learns geometry from synthetic photographs, then uses that geometry to straighten the original photo. The working sequence is **source films → simulated captures → training → fixed development checks → visual review**. Start with the [data-driven research story](research-journey.md) if you want to understand why the training recipe changed.

Choose the path that matches your assets:

| Your starting point | What you can do |
| --- | --- |
| Code only | Run the synthetic tests; no X-rays or weights needed. |
| New, authorized images already split into directories | Build and check a new data bundle in section 3. This prepares a **new experiment**, not a replay of the published results. |
| Original research bundle, initialization and checkpoint | Follow sections 4–6 to check and run the existing experiment. |

The current training entrypoint is tied to the original **4,114 train / 478 development / 28 quarantine** files and their exact manifests. A newly generated manifest does not become compatible by matching these counts. We do not provide a generic new-dataset fine-tuner here.

## 1. Install and check the environment

Use Linux, Python 3.11 or 3.12, and Keras with the PyTorch backend. The commands below use Python 3.12 and `uv`; have both installed first. Training needs a CUDA GPU supporting BF16. The tested training configuration used a 24 GiB RTX 4090 D and a 16-core CPU quota; confirm the resources on your own machine.

```bash
git clone https://github.com/wzxsph/RectiRay.git
cd RectiRay
uv venv --python 3.12
uv pip install --python .venv/bin/python -e '.[dev]'
export KERAS_BACKEND=torch
export RECTIRAY_ROOT="$PWD"
PY="$RECTIRAY_ROOT/.venv/bin/python"
"$PY" -c 'import torch, keras; print("torch", torch.__version__, "keras", keras.__version__, "CUDA", torch.cuda.is_available(), "BF16", torch.cuda.is_bf16_supported() if torch.cuda.is_available() else False)'
CUDA_VISIBLE_DEVICES='' "$PY" -m pytest -q
```

**Success:** synthetic tests pass. For GPU training, both CUDA and BF16 checks must be true. Installing the broad project dependencies does not reproduce an old CUDA environment exactly; `requirements.lock` records one environment snapshot, not a driver installer.

## 2. Keep data separate from code

Use the repository's ignored `.local/` directory. Inputs and generated bundles stay local; do not upload their images, manifests, reports or weights.

```text
.local/
  incoming/                  # new-data path only
    sources/{train,dev,quarantine}/
    backgrounds/{train,dev}/ # actual photographs; not generated viewer screens
    provenance.json          # optional source and license notes
  prepared/new-bundle/       # generated by prepare_data.py
  assets/                    # existing-experiment path: authorized original assets
    bundle/
      data/manifest.json
      data/split.json
      data/backgrounds-manifest.json
      ...                    # image files at the exact manifest-relative paths
      weights/b11.weights.h5
      weights/g0.pt
      weights/g0.json
    backgrounds/             # root for background manifest-relative paths
    start/step-2000.pt
    start/frozen-protocol.json
  runs/                      # checkpoints, state, training logs
  cache/                     # rebuildable synthesized inputs
  reviews/                   # local metrics and comparison pages
```

This public source repository does not distribute model weights. The three historical stage backups, containing trained checkpoints and metadata, are retained in a separate controlled private archive; the [checkpoint/source map](checkpoint-source-map.md) records the current location, hashes and source bindings. Those stage backups do **not** contain the original data bundle, the two initialization assets or the saved starting protocol. Obtain the required assets separately through authorized access; a backup download alone is insufficient. Dataset sources and permissions are listed in [THIRD_PARTY](../THIRD_PARTY.md).

## 3. Prepare new data, without changing the split

Put your already assigned images into the incoming directories above. `quarantine/` may be empty; train and development must each contain films and real-photo backgrounds. Keep related patients together when reliable grouping is available; the tool neither infers patient identity nor claims patient independence.

```bash
"$PY" tools/prepare_data.py \
  --sources "$RECTIRAY_ROOT/.local/incoming/sources" \
  --backgrounds "$RECTIRAY_ROOT/.local/incoming/backgrounds" \
  --output "$RECTIRAY_ROOT/.local/prepared/new-bundle"
"$PY" tools/check_assets.py --mode data \
  --bundle "$RECTIRAY_ROOT/.local/prepared/new-bundle" \
  --backgrounds "$RECTIRAY_ROOT/.local/prepared/new-bundle/backgrounds"
```

**Produces:** three loader-compatible manifests under `data/`, byte-for-byte film/background copies and a local preparation report. No image is resized or augmented during preparation. Stable ordering and hashes make repeat preparations comparable. The source files remain untouched.

**Success:** all files decode, hashes match, and no identical file or decoded image appears in both train and development. Quarantined duplicates are retained and reported. Existing output directories, symlinks and escaping paths are rejected; failed preparation does not publish a complete-looking bundle. The checker prints a JSON summary; add `--report "$RECTIRAY_ROOT/.local/reviews/data-check.json"` to save it to a new local file.

Add `--provenance "$RECTIRAY_ROOT/.local/incoming/provenance.json"` to record source and license notes. This is a record of your inputs, not a license or privacy approval. See `--help` for its format. Missing provenance is explicitly recorded as unspecified. Viewer screens and near/mixed-color surroundings are produced by the scene generator; you do not need 1,100 separate interface files for a new bundle. Historical bundles may retain those manifest entries unchanged.

**Stop this path here.** New bundles are preparation for a separately defined experiment; do not pass them to the fixed step-2000 training entrypoint.

## 4. Check the original experiment assets

For the remaining steps, use the **original bundle and manifest bytes**, not section 3's regenerated bundle. The commands start a new run with the current source. To replay a saved historical run, follow [the isolated-source instructions](#advanced-exact-historical-source-and-numerical-mode) **before its resume or evaluation check**. Set these paths once, from the repository root:

```bash
export BUNDLE="$RECTIRAY_ROOT/.local/assets/bundle"
export BACKGROUNDS="$RECTIRAY_ROOT/.local/assets/backgrounds"
export PARENT="$RECTIRAY_ROOT/.local/assets/start/step-2000.pt"
export PARENT_PROTOCOL="$RECTIRAY_ROOT/.local/assets/start/frozen-protocol.json"
export CACHE="$RECTIRAY_ROOT/.local/cache/rectiray"
export RUN="$RECTIRAY_ROOT/.local/runs/rectiray-01"
export TRAINING_SOURCE="$RECTIRAY_ROOT"
export PYTHONPATH="$TRAINING_SOURCE/src"
PARENT_SHA=016cfc5b3fb97699eb38b6ce8850c7d4802797602d8fba04f233959744120535
"$PY" tools/check_assets.py --mode start \
  --bundle "$BUNDLE" --backgrounds "$BACKGROUNDS" \
  --checkpoint "$PARENT" --checkpoint-sha256 "$PARENT_SHA" \
  --parent-protocol "$PARENT_PROTOCOL" --source-root "$TRAINING_SOURCE"
```

**Success:** the data, initialization, G0 sidecar, starting checkpoint and frozen development fingerprint agree. The checker reads all three film splits and every background row, including assets the training loader does not consume. It never rewrites the manifests.

The 2000-step checkpoint supplies both learned parameters and Adam state. The next run uses the revised recipe and a fresh deterministic sample sequence. This is continued learning with new data, not training from random initialization or a bitwise continuation of the old sample stream. The current renderer differs from the historical training renderer; use the isolated-source instructions below when reproducing a historical checkpoint exactly.

## 5. Preflight, train and resume

After section 4 passes, create a **separate CPU-only zero-step run**. This checks loading and writes initial state; it performs no optimizer updates. `--skip-training` skips the loader's image-file verification, so a successful zero-step run does **not** replace the full asset check:

```bash
CUDA_VISIBLE_DEVICES='' "$PY" -m ptrn_pipeline.step2000_runner \
  --bundle "$BUNDLE" --backgrounds "$BACKGROUNDS" --cache "$CACHE" \
  --parent "$PARENT" --parent-protocol "$PARENT_PROTOCOL" \
  --source-root "$TRAINING_SOURCE" \
  --output "$RECTIRAY_ROOT/.local/runs/preflight-01" --steps 3000 --skip-training
```

**Produces:** `branch-step-0.pt`, binding/provenance files and `sample-sequence.npy/json`. Keep this directory separate from the fresh training directory.

When ready to train on your allocated GPU, run:

```bash
"$PY" -m ptrn_pipeline.step2000_runner \
  --bundle "$BUNDLE" --backgrounds "$BACKGROUNDS" --cache "$CACHE" \
  --parent "$PARENT" --parent-protocol "$PARENT_PROTOCOL" \
  --source-root "$TRAINING_SOURCE" \
  --output "$RUN" --steps 3000 --gc-interval 4
```

**What happens:** up to 3,000 additional updates, 224-pixel input, actual/effective batch 64, Adam, frozen DenseNet201 and BatchNorm. CPU workers prepare scenes ahead of consumption; GPU updates and diagnostic predictions are interleaved while CPU metrics continue. A checkpoint is saved every 250 updates. The step count measures updates, not unique source images or epochs.

**Watch:** `training.jsonl` for updates/losses and `runner-status.json` for phase progress. Check `completion.json` separately for training and evaluation completion. Lower loss or completion alone is not evidence of good real-photo crops.

The runner saves immutable checkpoints but no checksum catalogue. Record their SHA-256 values on the machine that produced them, and keep the record when copying a run:

```bash
sha256sum "$RUN"/branch-step-*.pt > "$RUN/checkpoint-SHA256SUMS.txt"
```

To resume an interrupted run, retain the **entire original run directory**. Set `RESUME` to its latest intact saved checkpoint and `RESUME_SHA` to that file's digest in your saved checksum record. Do not use an unsaved printed step, roll back into a directory containing later checkpoints, or compute a new expected digest merely to bypass a mismatch. For Release assets, use the supplied checksum metadata. Then run:

```bash
"$PY" tools/check_assets.py --mode resume \
  --bundle "$BUNDLE" --backgrounds "$BACKGROUNDS" \
  --checkpoint "$RESUME" --checkpoint-sha256 "$RESUME_SHA" \
  --parent-protocol "$PARENT_PROTOCOL" --run "$RUN" \
  --source-root "$TRAINING_SOURCE" --steps 3000
"$PY" -m ptrn_pipeline.step2000_runner \
  --bundle "$BUNDLE" --backgrounds "$BACKGROUNDS" --cache "$CACHE" \
  --parent "$PARENT" --parent-protocol "$PARENT_PROTOCOL" \
  --source-root "$TRAINING_SOURCE" \
  --output "$RUN" --steps 3000 --gc-interval 4 --resume "$RESUME"
```

**Success:** checkpoint, optimizer, RNG, consumed cursor, sequence, code and assets agree. A lone Release `.pt` copied into an empty directory is not a resumable run. Do not change the target step count or repair a mismatch by editing a binding JSON.

## 6. Evaluate and inspect the result

Choose a checkpoint from the run and its recorded SHA as `CHECKPOINT` and `CHECKPOINT_SHA`. Choose an unused evaluation directory:

```bash
export EVAL="$RECTIRAY_ROOT/.local/reviews/dev-check-01"
"$PY" tools/check_assets.py --mode evaluate \
  --bundle "$BUNDLE" --backgrounds "$BACKGROUNDS" \
  --checkpoint "$CHECKPOINT" --checkpoint-sha256 "$CHECKPOINT_SHA" \
  --source-root "$TRAINING_SOURCE"
"$PY" -m ptrn_pipeline.evaluation prepare \
  --bundle "$BUNDLE" --backgrounds "$BACKGROUNDS" --cache "$CACHE" \
  --output "$RECTIRAY_ROOT/.local/reviews/dev-prepare-01" --workers 4
"$PY" -m ptrn_pipeline.evaluation predict \
  --bundle "$BUNDLE" --backgrounds "$BACKGROUNDS" --cache "$CACHE" \
  --checkpoint "$CHECKPOINT" --output "$EVAL" --batch 1 --workers 4 --graph
```

`prepare` caches the frozen scenes; `predict` runs GPU inference and starts CPU metric workers. Its return does **not** mean those workers finished. Wait for `metrics-complete.json` and `evaluation.json`; inspect `metrics-progress.json` while waiting. Any `inference-failed.json` or `metrics-failed.json` means the evaluation failed.

Then verify and summarize the full result:

```bash
"$PY" tools/summarize_development.py --run rectiray="$EVAL" \
  --output "$RECTIRAY_ROOT/.local/reviews/development-summary.json"
```

**Success:** all **5,736** unique fixed development views are present and their checkpoint/protocol bindings match. Repeat `--run label=directory` to compare complete evaluations. Look at additional film crop, background and geometry together; the 4,589 photographed views should be distinguished from keep-original views. The development set has already informed model selection; it is not independent real-photo accuracy.

For a local visual comparison, set `AUTHORIZED_PHOTOS` to your authorized photo directory and use named checkpoints. Return to the current renderer explicitly if you used a historical source tree:

```bash
export PYTHONPATH="$RECTIRAY_ROOT/src"
"$PY" tools/compare_real_photos.py --bundle "$BUNDLE" \
  --photos "$AUTHORIZED_PHOTOS" --checkpoint rectiray="$CHECKPOINT" \
  --output "$RECTIRAY_ROOT/.local/reviews/real-01" --allow-renderer-update
```

This CUDA tool writes an `index.html` and local audit alongside **copies of the photos**. Review retained film, extra background, straightening and uncertain edges. The 47 research photos were already exposed during development, lack reliable paired boundary truth and remain local. The renderer flag permits only the explicitly audited rendering change; it is not a general source-check bypass. When also comparing original pipeline checkpoints, add the narrowly scoped `--allow-parent-source-updates` flag described in the [source map](checkpoint-source-map.md).

## Which script does what?

| Entry | Inputs → result |
| --- | --- |
| `tools/prepare_data.py` | Pre-split image directories → new local bundle and provenance report; no augmentation or training. |
| `tools/check_assets.py` | Bundle plus optional checkpoint/run → CPU-only integrity and compatibility report; no data repairs. |
| `ptrn_pipeline.step2000_runner` | Original assets and starting checkpoint → training/checkpoints; `--skip-training` writes zero-step state only. |
| `ptrn_pipeline.evaluation prepare` / `predict` | Frozen development data/checkpoint → cache, predictions and asynchronous metrics. |
| `tools/summarize_development.py` | Complete evaluation directories → checked aggregate comparison. |
| `tools/compare_real_photos.py` | Authorized photos and checkpoints → local visual review; never an independent benchmark by itself. |

## Advanced: exact historical source and numerical mode

The current source retains the model contract but includes a later area-resampling renderer. For strict evaluation or resume of a saved historical checkpoint, create an isolated source tree; never overwrite the active `src` directory:

```bash
REPLAY="$RECTIRAY_ROOT/.local/replay-source"
git worktree add --detach "$REPLAY" HEAD
cp "$REPLAY/training-source-overlays/pipeline-parent/partial_geometry.py" \
  "$REPLAY/src/ptrn_hip/partial_geometry.py"
export TRAINING_SOURCE="$REPLAY"
export PYTHONPATH="$TRAINING_SOURCE/src"
```

For the earlier pipeline checkpoints, also copy `partial_data.py` and `partial_synthesis.py` from the same overlay directory. Rerun the asset checker against `--source-root "$TRAINING_SOURCE"`; **all recorded file hashes must match** before calling this a historical replay. See the [source map](checkpoint-source-map.md) for which files belong to each stage. Run the commands from the main repository root so the current checking tools remain available. This restores source compatibility, not a promise of bitwise-identical long GPU training across environments.

Keep the reference **batch 1 CUDA Graph / TF32** evaluation mode. Larger batches previously exceeded the established numerical tolerance; `--strict-fp32` is a separate audit mode, not an equivalent substitute. Training-time eager diagnostics are also distinct from reference evaluation. `--eval-limit` on training or `--count` on evaluation is a smoke test, never a complete result. See [AutoDL practice](autodl-training-practice.md) for resource scheduling, the Graph/pinned-memory failure, and GPU shutdown/download procedures.
