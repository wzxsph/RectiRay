# AutoDL 与 GPU 训练实践

> 本文保存当时的训练、故障和性能实测；其中“正在运行”“尚未完成”等措辞均是记录时点，不是当前训练终态。当前入口见[仓库 README](../README.md)，最终状态以受控运行目录的完成标记与检查点绑定为准。

本文把 2026-09-25 PTRN 实验的实际结果转成后续运行方法。实现入口见 [并行流水线](pipeline-v1.md)，本轮配置见 [pipeline-v1.json](../configs/pipeline-v1.json)。这些参数只在本轮模型、224 输入和 4090 D 上验证，换模型、输入尺寸、解冻范围或设备后必须重新测速。

## 1. 资源与费用原则

用户确认的原则：缩短训练加必要验证的总耗时，提前准备可预测的数据，减少 GPU 等 CPU；所有训练、必要评估与导出完成并落盘后，先关闭有卡实例，再以无卡模式开机下载权重和日志。不能为了等下载、写报告或等待会话回复而继续占用 GPU。

“全部完成”必须由训练、评估、导出等各阶段的终态决定，不以 GPU 利用率低或训练步数不动单独判断。缓存准备、保存权重和 CPU 指标计算也可能是正常工作。若有其他训练未完成，不关闭共享实例。

无卡模式保留实例数据但没有 GPU，CPU/RAM 配额也更小；只用于准备环境、文件传输和轻量检查，不在其中启动 12 进程合成、加载大型模型或重新跑验证。关机不等于删除或释放实例，不执行释放实例、重置镜像或清空数据盘。下载后的保留或关机遵从用户当前要求；长期保留与平台释放期限以控制台为准。

平台操作核对日期：2026-09-25。AutoDL 官方支持关机后以无卡模式开机及实例内 `/usr/bin/shutdown`；平台政策、配额与费用可能变化，执行前看当前页面。[官方省钱说明](https://www.autodl.com/docs/save_money/)

本次 `step2000` 新分支运行时，先在唯一的 4090D 实例上设置过 **2026-09-26 06:00 定时关机**；用户随后明确改为 **2026-09-26 03:30**，AutoDL 页面服务器时间 01:14 时确认“设置成功”并显示新的目标时间。平台只按固定时刻关机，**不检查训练或验证是否完成**；Luna 固定监控仍以完整终态为准，若提前完成则先关机、无卡重开并下载权重。接近 03:30 尚未完成时应报告风险，但不得自行延长用户指定的截止时间，也不能把定时关机当作“训练完成”的证据。

## 2. 本轮实际执行顺序

1. 本地隔离研究目录，保留原模型、合成实现、权重及评估规则；新流水线放入独立 `ptrn_pipeline` 包。确认源码与数据指纹，使用 SSH 密钥接入已授权服务器。
2. 本地先做 CPU、GPU 小规模代码验证；服务器核实实际 GPU、CPU cgroup 配额、内存、磁盘和依赖。无卡模式下提前上传环境和数据，开卡后只做必要的设备验证和计算。
3. 正式 224 训练继续使用实际/有效 batch 64，不因优化而重跑已完成的 5000 步。训练完成后保留原检查点，性能与故障试验使用独立 scratch 目录。
4. 固定 5736 张开发场景提前生成，保存无损网络输入与原尺度几何信息；训练数据按轮次和确定性游标提前准备。
5. 先核对批量推理的数值兼容性。batch 8/16/32 未通过原容差，保留 batch 1，使用兼容的 CUDA Graph 减少 Python 发起计算的开销。
6. GPU 执行训练更新及穿插的验证预测，CPU 工作池并行算指标。旧训练与新评估实际同时推进；新 runner 由同一 GPU 调度入口控制，不无约束地并跑两个大模型进程。
7. 对 500、1250 检查点完成全开发集兼容性对照；对 47 张已授权手机照片检查原/新推理输出一致性；注入缓存损坏、工作进程退出与指标失败，检查是否正确失败和是否影响训练。
8. GC 间隔 1/4/8 各做 500 步对照，补充恢复检查、三次配对冷/热缓存测速和 GPU 新渲染数据审计。速度收益不替代数值与完整性要求。
9. 5000 步正式训练及 5736 张完整验证结束，候选权重备份本地并核对 SHA256；固定 Luna 任务记录终态并暂停轮询。实例的关机、无卡重开与下载回执单独留在本地运行记录。

## 3. 显卡训练经验

### 环境验证要区分本地、云端与无卡模式

本轮服务器使用独立 venv：Python 3.12、PyTorch 2.12.1+cu130、Keras 3.15.1，设置 `KERAS_BACKEND=torch`。本地 GPU 验证设备为 RTX 3000 Ada 8 GiB；代码能运行不等于本地 batch 可以直接搬到 24 GiB 云卡，反之亦然。保存实际版本清单，不能仅凭 `pip install` 成功断言 GPU 环境正确。

无卡阶段检查导入、路径、数据绑定、CPU 几何与缓存；有卡阶段再核对可用设备、一次前向/反向、优化器更新、保存/恢复及峰值显存。CPU 专用夹具明确使用 `CUDA_VISIBLE_DEVICES=''`，否则 Keras 自动选 GPU 而测试张量留在 CPU，会产生设备不一致的假故障。不要为此修改模型或降低测试断言。

部署新代码到独立目录，原训练进程继续运行。到持久检查点后再切换，核对源代码、权重 SHA、BN 状态、优化器与游标；已经完成的训练步骤不因新流水线部署而重跑。凭据只保存在受控连接配置，日志和文档中不打印密码或私钥。

### 显存使用率不等于吞吐

本轮为 RTX 4090 D 24 GiB、16 核 CPU 配额、约 60 GiB RAM。显存有空余并不自动意味着应增大 batch：还应看算子利用率、CPU 发起开销、供数、传输及验证耗时。实际 batch 决定每步设备负载，有效 batch 还可能包含梯度累积，二者应分别记录。

在相同模型/数据/精度下测多个候选 batch，记录吞吐、步耗时分布、峰值显存及质量兼容性；给验证模型、图捕获和临时张量留空间。本轮 GPU 总预算为 22 GiB，实际/有效 batch 均为 64。增大分辨率或开放更多主干层时，这个配置不能直接照搬。

### 先消除等待，再选择计算设备

CPU 工作池在训练前准备输入，训练中维持有界预取；固定页内存配合独立 CUDA 传输流和双缓冲，CUDA 事件保证缓冲在消费前不会被覆盖。恢复从已消费的数据游标继续，不能用后台生产完成的游标代替训练游标。

固定验证只合成一次，后续检查点复用。训练缓存包含轮次、母片、场景种子、输入尺寸、背景与渲染代码版本，防止缓存意外冻结数据增强。图片保留 uint8、浮点标签保留 float32，不再用 JPEG 二次压缩缓存。

GPU 合成不是默认更快。本轮新版本包含 CPU 解码/参数/缺损几何、GPU 采样与外观、异步回传及后台写盘。常驻 CPU 工作池下，1024 张输入的 CPU 在线供数加训练约 10 秒，而 GPU 预生成、读盘加训练约 32～36 秒。计入全流程后未达到 10% 收益要求，因此默认 CPU 提前合成和缓存。首次进程启动会夸大 CPU 耗时，必须另报热工作池结果。

### 验证与训练可以重叠，但要分清职责

GPU 预测绑定冻结检查点，不能在评估途中混用训练更新后的权重。预测按分片落盘，CPU 指标继续处理；GPU 无需等 CPU 指标全部完成才训练。单卡通过交错调度维持显存与资源上限，不承诺两个大 CUDA 任务在每一时刻都同时执行。

每个结果绑定检查点 SHA、场景版本、精度和样本编号；完整验证必须覆盖全部 5736 张且无重复。指标进程失败应标记该评估失败，健康训练仍可继续；NaN、损坏权重或数据绑定不符则停止相关训练。最终交付前仍需处理必要评估的失败。

并行验证还要检查 CUDA 调用是否来自后台线程。本轮新分支证明：即使训练与验证由一个主线程调度，`DataLoader` 的固定页内存线程和 H2D 预取仍可能在 Graph 捕获窗口工作。训练期间使用通过并发实测的 eager 诊断；要求旧数值口径的 CUDA Graph 审计安排在输入线程关闭后。

### 数值一致性应与性能分开审计

严格 FP32 与 TF32 各有自己的参考，不混用。批量改变造成超容差时缩小 batch，不降低断言。CUDA Graph 的捕获范围、张量地址和生命周期也需要明确检查。

原 CUDA 反向计算自身存在非确定性，长程参数不能保证逐位相同；这不允许把所有差异笼统归因于 GPU。加载瞬间仍严格核对权重、Adam、RNG 与数据游标；CPU 确定性更新用于独立检查计算一致性，原 GPU A/A 对照及失败记录保留。

## 4. 本轮测量与适用范围

| 项目 | 实测结论 | 限制 |
|---|---|---|
| GC 间隔 1 / 4 / 8 | 0.411 / 0.300 / 0.287 秒每步 | 各 500 步；8 的末段显存分配波动 133.22 MiB，超过 128 MiB 限制，选 4 |
| 热训练缓存 | batch 64 约 0.314 秒每步；取数等待约 0.0021% | 预生成 5120 个输入、80 步测量，不代表无限长冷缓存训练 |
| 完整 1250 检查点验证 | 旧串行约 28.6 分钟；新预测与指标阶段约 77 秒 | 新计时不包含首次缓存、输入库与模型初始化 |
| 完整 5000 检查点冷流程 | 从空开发缓存生成到指标结束约 313.5 秒 | 同检查点结果一致；不可与旧 1250 时间作为严格配对比较 |
| 三次配对性能检查 | 固定 256 张、同检查点同顺序，冷/热分开 | 不是三次 5736 张全量测速 |
| 实拍兼容性 | 47 张的新旧流水线输出像素、有效掩码一致 | 证明执行路径兼容，不证明模型取图正确 |

资源配额：主进程最多 4 线程；无指标任务时准备 12 个单线程进程，有指标时准备 8、指标 4。开发缓存最多 12 GiB，训练所有版本合计 8 GiB，总计 20 GiB，至少留 15 GiB 磁盘。RAM 输入缓存最多 8 GiB，固定页缓冲最多 1 GiB，进程组内存超过 48 GiB 暂停生产。

这些限制应按 cgroup 实际配额设定，不能直接把宿主机逻辑 CPU 数当成可用核数。只清理能重建的缓存，不清理原片、正式检查点和评估结果来掩盖磁盘不足。

### 2026-09-26：step 2000 新分支中断与恢复记录

**触发与影响。**统一新配方从旧 `step-2000.pt` 建立独立分支，父权重 SHA256 为 `016cfc5b3fb97699eb38b6ce8850c7d4802797602d8fba04f233959744120535`。首次运行 `run-20260926` 已保存新增第 250 步检查点；`training.jsonl` 记录到 +270／游标 17280，随后读取下一批时中断。`console.log` 第 28–73 行的 traceback 显示主线程在 `next(buffer)` 等待后台数据，PyTorch 报 `Caught AcceleratorError in pin memory thread for device 0`，底层为 `CUDA error: operation not permitted when stream is capturing`。训练循环使用 `DataLoader(pin_memory=True)` 和独立线程提前把下一批传入 GPU；+250 检查点入队时，验证任务默认创建 batch 1 `GraphPredictor` 并开始 Graph 捕获。首个验证目录为空，没有写入绑定或预测，符合初始化期失败，不能称为 Graph replay 故障。**异步 CUDA 错误在 +250 附近触发、到 +270 后取数时才显现**，因此定位要回查首次验证启动，而不只看报错时的训练步。证据指向两条并发 CUDA 路径相互干扰，不能仅凭异常栈断言更深层的驱动或框架缺陷，也不能据此判断模型或训练标签有问题。+270 虽有日志，但没有落盘检查点；恢复点只能是已核验的 +250，失败运行及其不完整验证产物保留用于追溯。

**为什么预检没发现。**此前分别测过 CUDA Graph 预测和固定页内存供数，但没有在真实训练调度下覆盖“后台传输正在运行时启动 Graph 捕获”。“只有一个主 GPU 调度入口”仍可能有后台线程在调用 CUDA；检查进程数和显存占用不足以证明捕获窗口独占。以后凡是引入 Graph、异步 H2D、预取或并发验证，必须增加同进程 GPU 集成测试：让真实 `DataLoader`、固定页内存线程和双缓冲持续工作，跨过首个检查点启动验证，再检查下一批训练、预测分片、指标、异常和退出清理。隔离的单模块测试只验证各自路径，不代替这项交叉测试。

**修复与数值口径。**独占 GPU 的隔离测试中，batch 1 CUDA Graph 成功预测 8 张固定开发图；eager 预测与训练固定页内存传输并行的 8 张实机测试也通过。因此恢复版在训练期间用 eager 模式做诊断预测，保留 CPU 指标与训练重叠；待训练输入线程全部退出，再用 batch 1 CUDA Graph 对父权重及必要分支权重做完整 5736 张严格验证。eager 诊断与旧 CUDA Graph 参考不可混称为完全等价；最终检查仍按原数值容差和完整样本数判断，不因这个修复放宽门槛。将来若重新允许边训练边捕获 Graph，先在相同 GPU、线程和数据流配置下通过上述交叉测试，不凭独立 Graph 测试推断安全。

**恢复审计。**第 250 步原检查点 SHA256 为 `bff2b147382aa724fda37a57e6353cea55b9b4b9faef84b347fcc42d084c8c39`。修复更改了代码绑定，原恢复校验拒绝直接加载是预期保护；不能为了续跑删除绑定检查。使用独立迁移工具生成新检查点（SHA256 `10a1106c929756b5adae9a41cdfffc0d8ef4d8435587030209ff9c5955213377`），逐项核对模型权重、Adam、CPU/CUDA 随机状态与已消费 16000 张次游标保持不变，并确认数据资产、合成配方、样本顺序和开发集指纹未变。只允许审计过的训练编排代码与迁移工具进入代码 SHA 差异。新运行 `run-20260926-r3` 从 +250 接续，不重放已持久保存的优化步，也不把失败时达到的 +270 当作有效检查点。

**恢复后的观察与后续门禁。**隔离的 Graph 预测及与固定页内存传输并行的 eager 预测各完成 8/8 张；r3 的 +250、+500 eager 诊断各完成 512/512 张预测与指标。r3 训练日志从 +251 接续，没有重放 +1～+250；这证明已跑过首次故障点，但 8 张烟测和 512 张诊断都不能代替最终 5736 张严格验证。CPU 合成新配方一度造成明显取数等待；开发缓存准备完成并调整为主进程 2 线程、训练生产者 10–14 个进程后，短窗口曾观察到取数等待接近零，但评估并行时仍可能重新出现 CPU 供数瓶颈。供数速度问题与本次捕获异常分开记录，按整轮训练加验证耗时判断，不能把短窗口当作整轮吞吐。只有训练完成、所需严格 Graph 验证完整落盘且无评估错误，才能标记本轮计算完成；实拍 47 张效果还要单独审阅。**截至此记录，训练与最终严格验证尚未完成。**

## 5. 后续每次训练的收尾方法

1. 在服务器保存并核对最终检查点、恢复状态、配置、依赖版本、源码/数据指纹、全部必要评估和日志；权重记录文件大小与 SHA256。先完成落盘与校验，不为大批下载继续开着 GPU。
2. 核对本实例没有其他未完成训练、验证、导出或写盘进程；写入持久化完成状态，停止本任务的后台生产与采样。固定 Luna 监控平时只读，按本轮用户授权可在确认全部完成后执行关机与无卡重开；故障时不自动恢复或改训练。
3. 已获用户授权时，由执行任务在控制台正常关机，或使用官方 `/usr/bin/shutdown`；核实控制台出现“已关机”。不把 SSH 断开单独当作关机证据。
4. 在同一实例选择“无卡模式开机”，核实模式与小资源配额，使用当前 SSH 地址连接。不能点击正常 GPU 开机来下载；也不能新租一台机器替代原实例。
5. 只下载缺少的权重、配置和结果；已有文件先比大小与 SHA，相同则跳过。下载先落到 `.part`，校验通过再原子改名。大文件流式传输，不在无卡实例整包载入内存或启动模型。
6. 保存下载清单与 SHA 校验回执。模型权重、真实影像及详细结果仍只在受控本地/已授权服务器；不写入普通 Git，不自动替换应用模型。
7. 下载结束后报告当前模式和传输结果，按用户要求保留无卡运行或再次关机。用户在控制台手动调整模式时，以最新状态为准，不与用户反复开关机；下载中断先保留断点。后续需要 GPU 时重新核查空闲资源与配置，不保证原卡被保留。

上述是人工/执行任务的操作流程，当前训练代码没有默认增加自动关机钩子。若以后接入自动关机，必须等待所有必要阶段终态、文件落盘和实例独占核查，不能简单以 `train.py` 返回或 GPU 低利用率为条件。
